## 列表与实际 HTTP 性能

修改前：读取 10 条需要 72 次核心业务 SQL，29 条需要 197 次。修改后：整页批量详情为 6 次，页面摘要为 3 次；页长 10 与 100 均保持相同查询数。单条完整详情按选中记录加载。所有关联批量查询保留组织约束。

原 SQL 使用的查询计划与新索引计划分别记录在 `sql-before.json`、`sql-after.json`。新增 `(org_id, run_id, id)` 和状态分页索引；没有引入外部搜索服务。

首轮整页候选详情负载：列表 P95 572.9 ms，高于 500 ms 建议目标。改为摘要列表后进行了第二轮完整 15 分钟测量：

| 接口 | 请求数 | P50 | P95 | P99 |
| --- | ---: | ---: | ---: | ---: |
| 摘要列表（50 条） | 5417 | 82.5 | 109.7 | 123.8 |
| 选中记录候选详情 | 895 | 51.6 | 61.3 | 83.3 |
| 审核提交 | 1290 | 54.8 | 93.0 | 116.6 |
| 运行列表 | 410 | 71.7 | 91.1 | 102.7 |
| 导出列表 | 453 | 38.5 | 51.3 | 56.2 |
| 标准库搜索 | 455 | 37.6 | 50.8 | 55.4 |

表中延迟单位为毫秒。第二轮共 **8,920 次请求**，非预期 5xx / 网络错误 **0**，业务版本冲突 **2 次**，单独计入 409。API 进程采样峰值 RSS **187.3 MB**，采样 CPU 峰值 **76.5%**（本机进程口径）。

环境：macOS 26.6.2 ARM64，Python 3.12.14，SQLite WAL，Uvicorn，真实 TCP HTTP，10 个独立认证的模拟用户。任务含 1 万条来源记录、4 个历史运行，12 件演示标准商品；来源编号唯一，商品来自受控重复构造。每用户约 1 秒一个请求周期。第二轮增加了独立详情请求，并减少部分运行/搜索请求，不能将前后差异解释为完全相同负载下的纯 SQL 因果收益。

上述结果达到本轮本地负载下的列表 <500 ms、审核 <300 ms 建议值。它不代表 5 万标准商品、非规则业务数据、真实网络或 PostgreSQL 的性能结论；数据库连接等待包含在总延迟中，尚未单独采集。

## 模型一致性与实验结果

固定输入取 33 条查询、660 个候选配对。离线冻结词表特征和直接 Booster 打分，与 Worker 使用的 Matcher 打分核心对照：最大特征误差 **0.0**，最大分数误差 **0.0**，容差 1e-6，排序与最终状态相同。这是计算核心的数值验证，不是 HTTP 性能或真人准确率验证。

受控模拟 test 分区含 120 个实体 / 360 条查询，其中 327 条在库、33 条无匹配。规则、字符 TF-IDF+规格约束及 LightGBM 在这批数据上均得到：Recall@20=100%、推荐精确率点估计=100%、覆盖率=60.56%、端到端推荐召回=66.67%。只有 109 个独立推荐实体。

推荐精确率的实体保守 95% 区间为 **96.60%–100%**。无匹配误推荐点估计为 0%，但仅 11 个独立无匹配实体，Wilson 95% 区间上界约 **25.88%**，不能宣称真实误推荐率 ≤1%。模拟数据资格不足、独立推荐实体少于 200，且精确率区间下界低于 98%，因此没有发布学习策略。

困难负样本从训练分区实际召回候选中采样，训练目标也限定为训练实体。采样清单、四次调参、阈值搜索、整系列留出、分切片分母见 `phone-experiment.json` 和 `models/phone-sim-v1/`。固定 10 分箱报告 Brier/ECE；本轮校准未显示收益，不作模型优于规则的业务声明。原 Abt-Buy 结果保留为混合品类公开基准，未拿来替代手机业务准入。

## 产品流程与数据正确性

后端回归验证了文件重排的业务差异为零；修改 5 条容量只产生 5 条身份变化；重复或缺失编号进入歧义列表。补数测试验证草稿版本冲突、操作者权限、不可变原始来源、仅 1 条受影响记录的新运行、资料依据、双人审核与重复提交幂等。补数与原运行直接比较时只对照涉及的来源。

浏览器实际操作覆盖上传 / 解析 / 映射 / 校验 / 匹配 / 人审 / 导出 / 撤销、完整问题下载、补数、影子比较、摘要与详情分离读取、运行状态和 390 px 页面。截图及录屏位于 `docs/optimization/browser/`，原业务浏览器回归位于 `browser-regression/`。

SQLite 增量升级前后，2 个组织、3 个输入版本、3 个运行、90 条来源、3 条审核事件及 1 个导出的数量一致。未清空业务数据库。迁移后已通过 Alembic 结构一致性检查。

## 恢复与运维证据

真实 Worker 进程在领取分块后被 SIGKILL。没有人为修改租约时间，使用普通处理轮询等待自然过期；**120.88 秒**后观察到恢复，低于 180 秒建议目标。最终 29 条结果 / 29 个唯一来源，重复投递未产生重复记录，旧 fencing token 提交被拒绝。此为本地 SQLite 路径证据，不能代替 Celery 生产 Worker 恢复。

到期导出清理测试先注入存储失败，再恢复删除操作，验证任务重试、对象物理删除、410 下载响应及保留快照/哈希。此存储错误为受控故障注入，非真实 MinIO 停机。

完整备份恢复到新目录后，验证了 **23 个文件**和 **6 个被引用对象**，并实际验证组织隔离、历史审核、可用导出、模型与冻结词表加载。模型通过 `MODEL_DIR` 和稳定制品 ID 重新定位。恢复过程中未依赖旧模型绝对路径。

本机无 Docker。Compose、资源限制与告警 YAML 已解析；PostgreSQL DDL 已生成；`scripts/stack_drill.py` 提供可执行的隔离部署和 Redis 真实中断检查，但本轮未运行。仍须在可用环境完成：空栈至导出、真实 Redis / PostgreSQL / MinIO 故障、Celery Worker 自然恢复、4 核 16GB 下 1 万 × 5 万的分段耗时及两个 Worker 的总内存。原 1.0 容量数字只作历史基线，本轮未把它们标为新资源配置验收。

- 恢复：`python -m scripts.natural_lease_drill`、`python -m scripts.backup`、`scripts/verify_restore.py`；后者以交付演示账号和既有历史记录为验证样本。
