# v1.2 运行与工程验收

## 当前配置与验收边界

本机已运行 SQLite WAL、独立数据库调度器和静态 Vue 网页。标准库/输入/审核/发布历史保留。本机测试不能替代 PostgreSQL、Redis、Celery、MinIO、反向代理组合的验收。

| 配置 | 默认值 |
|---|---|
| 组织活动匹配运行 | 1 |
| 全局活动匹配运行 | 2 |
| 每组织活动与排队匹配总数 | 20，可配置 1–100 |
| 每成员/服务账号每分钟请求 | 1,200，可配置 |
| 每组织对象配额 | 1 GiB，可配置 |
| 审核领取 / 续期 | 300 秒 / 每 60 秒 |
| 匹配分块 / 租约 | 200 条 / 120 秒 |
| 交付尝试租约 / 自动尝试上限 | 30 秒 / 8 次 |

本地匹配与短任务使用独立线程池，Compose 分为 match、short 队列。匹配调度优先较久未获得执行机会的组织；发件箱按组织及任务种类交错读取。默认数据库调度轮询 2 秒，重投扫描使用 30 秒窗口。资源隔离和持续大量提交下的生产公平性仍需压测。

对象按内容哈希去重预占，重试不会重复收费。升级时执行完整存储盘点，计入历史文件、导出、解析缓存和已存在的孤立对象。数据库事务回滚后可能遗留尚未盘点的对象；对象配额不是文件系统硬配额，磁盘容量需监控并周期盘点。盘点不删除任何数据。

## 升级现有本地数据

先停止该项目 API 和 Worker，保留旧应用包。不要用初始化或清空数据代替升级。

```bash
python -m scripts.upgrade --backup /path/to/new-v11-backup
python -m scripts.reconcile_storage
python -m alembic check
python -m scripts.dev
```

目标迁移版本为 `9b7798dcda5b`。升级脚本自动备份，只识别当前或已知旧结构；未知未标版本数据库会停止并保留备份。已验证空库、带版本的 v1.1 副本及未标版本的已知 v1.1 结构。原始数据逐表比较证据见 `enterprise/upgrade.json`。

演示环境可另行执行 `python -m scripts.demo_enterprise`，只为密码仍符合已知构造演示账号的成员添加企业角色，不处理其他账号。真实组织通过成员管理显式授予角色。

回退先判断故障类型：兼容性允许时回退应用，否则向前修复或恢复完整备份。不要把应用回退等同于删除新表；不支持在有发布/回执记录时直接降级数据库。

## 备份、恢复与交付暂停

```bash
python -m scripts.backup create /path/to/new-backup
python -m scripts.backup verify /path/to/new-backup
python -m scripts.backup restore /path/to/new-backup /path/to/fresh-restore
DATA_DIR=/path/to/fresh-restore MODEL_DIR=/path/to/fresh-restore/models python -m scripts.dev --port 18766
```

备份包含数据库、对象、模型、冻结词表、数据集清单、会话密钥；若环境变量提供 JWT_SECRET 或 INTEGRATION_MASTER_KEY，另存权限为 0600 的 recovery-keys.json。恢复启动前应从此受保护文件恢复对应环境配置，不要生成新密钥替换。禁止把备份或凭据提交到源码仓库。

存在非 APPLIED 交付时，恢复目录自动生成 `delivery-restore-hold.json`，后台暂停发送。先将原 event_id 与接收方持久处理记录逐条对账，再由维护人员记录依据并解除：

```bash
DATA_DIR=/path/to/fresh-restore python -m scripts.reconcile_restore --acknowledge-reconciliation --reason "已按事件编号与接收方对账，记录工单及处理人"
```

本轮验证 34 个备份文件、15 个发布制品、121 条历史审核事件和 1 条待交付通知，恢复后原哈希、租户隔离、模型加载和签名密钥均通过。证据 `enterprise/restore.json`。这是本地演练，不声明生产 RPO/RTO 已达标。生产目标暂定 RPO ≤24 小时、RTO ≤2 小时，须在客户环境完成备份频率和恢复计时验收。

## 容器与监控配置

```bash
python -m scripts.init_env
# 在 .env 配置真实域名、HTTPS cookie、出站白名单与 Grafana 密码
# GRAFANA_PASSWORD 必须显式设置

docker compose up --build -d
docker compose -f compose.yaml -f deploy/compose.monitoring.yaml --profile monitoring up -d
```

API/Worker 使用受保护的 `var/secrets/metrics_token`。父目录权限为 0700；令牌文件 0644 以便 Compose 文件挂载后不同非 root 容器用户读取，主机其他用户不能穿过父目录。API `/api/v1/internal/metrics` 和 Worker `/metrics` 只接受专用 Bearer 指标凭据，业务角色不能替代该身份。进程级计数重启会清零，应按实例聚合；业务/队列全局量由 API 查询持久数据库，多个 API 副本时以 max 等方式去重，不能累加成重复业务量。

Grafana 和 Prometheus 配置已准备，尚未启动验证。持久量包括队列最老等待、过期租约、发件箱、发布文件和交付状态；进程量包括接口延迟/错误、Worker 执行、连接占用和内存峰值。数据库连接等待、锁等待未单独埋点，当前不能提供该分段证据。磁盘量是应用数据目录所在文件系统，MinIO 容量需另外接入对象存储监控。

探针：`/api/v1/live` 仅验证进程；`/health` 检查数据库；`/readiness` 检查数据库、队列和存储。Redis 不可用时可降级登记任务，数据库不可用时 readiness 返回 503，存储不可用时也返回 503。

通知签名密钥加密保存。可设置 INTEGRATION_MASTER_KEY 为 Fernet 密钥；未设置时由 JWT_SECRET 派生，因此必须保存同一密钥配置。生产通知地址须在 WEBHOOK_ALLOWED_HOSTS 中且使用 HTTPS；解析地址校验后固定连接 IP，保留 TLS 主机校验并拒绝重定向。本机模拟才可设置 WEBHOOK_ALLOW_LOOPBACK=true 并白名单 127.0.0.1。

## 目标环境仍需执行的验收

`scripts.stack_drill --output /path/to/isolated-evidence --port 18800` 准备独立 Compose 工程，当前脚本覆盖启动、种子流程、Redis 中断期间登记、恢复匹配和导出。它没有自动覆盖下表全部场景；脚本成功不能宣称完整生产验收。

| 待验收场景 | 操作与通过条件 |
|---|---|
| PostgreSQL/MinIO/Redis/Celery 全流程 | 空库迁移，登录→导入→审核→补数→完整发布→通知→回执；保存依赖版本与配置摘要 |
| Celery 进程中断 | 对真实正在处理分块的 Worker 子进程 SIGKILL，不修改 lease_until；自然到期后观察恢复开始时间及旧令牌拒绝 |
| PostgreSQL 中断 | 在专用 acceptance 工程停止数据库并提交审核/发布；恢复后核对事务未产生半份决定或重复发布 |
| MinIO 中断 | 生成发布文件时停止对象存储；文件未就绪应不可下载/通知；恢复后重试并核对相同快照哈希 |
| 4 CPU / 16 GiB 容量 | 使用 deploy/compose.acceptance.yaml，10 人节奏至少 30 分钟；独立测 API、后台及混合，含多历史版本、发布校验/下载及持续双组织排队 |
| 监控恢复 | 配置真实值班负责人、告警渠道和升级路径；触发告警→关联资源定位→恢复→告警解除，保存时间线 |
| PostgreSQL/MinIO 恢复 | 暂停写入，pg_dump 与 mc mirror 配套备份，保留密钥/模型；独立恢复并对账待交付事件，计量丢失窗口和恢复耗时 |

本机无 Docker/Podman/Colima、PostgreSQL 或 Redis 服务，相关生产组合未启动。CI 已提供 PostgreSQL 服务、迁移及关键事务测试配置，本次未在 GitHub 执行。生成 PostgreSQL DDL 是静态检查，不能替代真实数据库测试。

OIDC、SAML/SCIM 与高可用属于依赖客户环境的 P2 项，当前未实现。没有连续 30 天观测，不能宣称月可用性 99.5%。
