# 商品数据匹配平台优化方案

版本 1.0　评审日期 2026年9月10日

本方案面向项目下一阶段开发与求职展示。建议优先完成目标业务算法评测、模型流水线一致性、审核效率和真实部署验证，使已有业务闭环具备可量化的效果与交付证据。现阶段继续围绕手机 SKU 深化，比同时扩展多个品类更容易形成可信成果。

评审对象为 new-chat/outputs/product-match 中的使用说明、交付验收报告、模型实验报告及相关代码。验收数字引用已有报告；代码结论来自静态核对。本次未重新运行测试、压测或部署，也未修改项目代码。下文验收目标均为建议值，不代表当前已达到。

## 1 当前基础与主要判断

项目已经具备上传、字段映射、匹配、人工审核、导出和版本追溯的完整流程。租户隔离、乐观锁、幂等、任务租约、重复消息处理、撤销后的导出标记等设计已落地，应在后续优化中保留这些约束。

| 维度 | 已有证据 | 尚不能证明的能力 |
| --- | --- | --- |
| 业务正确性 | 报告记录 39 项 Python 测试通过，12 个浏览器检查点通过 | 真实业务人员长期使用的效率与误操作率 |
| 批量处理 | 构造数据 1万来源 × 5万标准商品，93.39秒，峰值 RSS 775MB | 非规则供应商数据的匹配质量；目标服务器表现 |
| 接口性能 | SQLite 进程内测试，29条记录，100次列表请求 P95 747ms | 大任务、多历史批次及真实网络下的体验 |
| 算法实验 | Abt-Buy 三种子平均 F1 0.6819；seed 42 精确率 0.6130 | 手机 SKU 高推荐精确率、全库召回和未见实体泛化 |
| 企业部署 | Compose 配置、迁移、队列与对象存储适配已提供 | PostgreSQL、Redis、Celery、MinIO 组合实际通过验收 |

优先级定义：P0 表示进入业务试用或发布学习策略前需要完成；P1 表示提高使用效率和维护能力；P2 表示获得前期证据后再投入。P0 不意味着现有演示版本不能使用。

## 3 算法优化方案

### 3.1 建立能够评价真实任务的数据集

目前训练回答的是“给定这两条记录，是否匹配”，产品面对的是“从完整标准库中选出正确 SKU，或者判断没有匹配”。应保留 Abt-Buy 实验作为公开基准，同时新增手机领域完整流程评测。200 对构造中文案例继续用于规则回归，单独报告，不合并成真实业务准确率。

建议首轮准备 300至500 个标准 SKU、800至1500 条来源记录，覆盖品牌、型号、内存、存储、颜色、地区版本和包装数量。样本分为两层：获得使用许可的公开记录用于目标领域评测；独立设计的合成供应商表用于格式扰动、冲突、缺字段和容量测试。记录数据来源、授权条件、获取日期和处理规则；没有真实来源时明确报告为受控模拟实验。

标注最小字段包括 query_id、entity_id、catalog_version、来源、原始字段、是否在标准库存在、匹配依据、标注人及复核状态。由两名标注者独立判断，分歧经复核后纳入冻结测试集。不能仅凭当前系统的规则输出生成测试真值，也不能仅凭名称相似就认定为同一 SKU。

训练、调参、校准、阈值选择和测试按完整 SKU 实体分组，别名与近重复记录随实体进入同一分区。测试查询对应的标准商品仍应存在于测试候选库中；“训练未见实体”不等于“标准库不存在”。另设型号系列留出集衡量更难的泛化，并记录右侧记录重用与近重复审计结果。

无匹配样本要独立构造和核验，可移除某实体在候选库中的全部标准记录，再加入相近但规格不同的干扰项。只删除一个正例配对不足以证明无匹配。测试集冻结后不用于挖训练负样本或选择阈值。

### 3.2 用推荐质量与覆盖率决定上线

当前 seed 42 分类阈值为 0.22，以 F1 最优选择；它不是业务高推荐阈值。误配 SKU 会影响采购和核对，因此应先约束推荐精确率，再最大化覆盖率。模型分数不直接显示为“正确概率”，除非已有目标领域校准证据。

| 指标 | 统计口径 | 建议初始目标 |
| --- | --- | --- |
| Recall@20 | 存在匹配的查询中，前20候选含正确 SKU 的比例 | 至少95% |
| 高推荐精确率 | 高推荐首选正确数 / 全部高推荐数 | 点估计至少98%，同时报告95%区间 |
| 推荐覆盖率 | 高推荐查询数 / 全部查询数 | 初始争取至少30%，精度不达标时允许下降 |
| 无匹配误推荐率 | 无匹配查询中被高推荐的比例 | 不高于1%，同时报告区间 |
| 端到端召回率 | 正确高推荐数 / 存在匹配的查询数 | 持续报告，防止仅靠少推荐改善精度 |

分别报告缺字段、规格冲突、别名、未见实体和无匹配切片，提供实体数、查询数和被推荐数。无推荐时精确率应标为不可估计，不应记为100%。按实体分组 bootstrap 计算区间；无匹配事件稀少时补充适当的二项比例区间，避免零错误导致虚假的零宽区间。

建议将“可以试用”与“可宣称稳定达标”分开：点估计达标且有至少200个独立被推荐实体时，可进入人工必审的有限试用；要宣称精确率稳定达到98%，应要求预先约定的区间下界也达到98%。首轮数据未必足以满足这一条件，应扩大独立样本量，而不是反复筛选测试集。

### 3.3 统一训练与在线特征生成

静态核对发现：训练脚本使用训练配对涉及的文本拟合 TF-IDF，max_features 为80000，并保存词表；在线 Matcher 在当前标准库重新拟合，max_features 为150000。即使特征名称一致，tfidf 数值的生成过程也不同。当前模型处于 EXPERIMENTAL，因此这属于模型启用前应解决的一致性问题，不能据此断言已发生线上误配。

建议将“候选召回索引”与“模型输入的文本相似度”明确分开：召回索引可以按标准库版本构建；模型打分使用随模型发布的冻结词表和相同计算函数。若决定使用随标准库变化的 IDF，则必须在训练和端到端评测中复现该机制，每个适用标准库版本重新验证，不能直接沿用配对分类报告。

发布清单至少绑定模型、词表、标准化规则、特征顺序、校准器、召回配置、推荐阈值、候选分差、适用品类以及评测集版本的哈希。为固定输入建立离线与服务端特征一致性检查，浮点容差建议1e-6；核对分数、排序和最终推荐状态。阈值、词表或规则变化应生成新策略版本。

### 3.4 将模型准入落实到完整策略

当前注册脚本创建 EXPERIMENTAL 模型；API 检查 AVAILABLE 和模型文件哈希，但创建策略仍允许单独指定推荐阈值与分差。仅校验模型状态，不能证明新阈值组合通过相同业务验收。

新增独立的策略评测和晋级入口，读取冻结报告并校验整个发布清单。通过后生成不可修改的策略版本；阈值变更重新评测。保留人工审核，并先运行影子对照：相同输入同时得到规则和学习策略结果，学习策略不改写现有决定。报告首选变更、硬冲突、覆盖率和人工纠正率后，再允许新任务选择该策略。

验收至少覆盖：未达标报告不能晋级；报告与模型、词表或阈值不一致时拒绝发布；旧策略可继续复现；切回上一策略只影响新运行，历史决定与导出快照不变。

### 3.5 先做困难负样本和公平基线

目前规则基线为手机规格设计，Abt-Buy 覆盖混合电子商品，因此 F1 从0.3224到0.6852不能解释为对同领域强基线的普遍领先。下一轮建议在同一手机数据划分、相同候选预算和相同业务门槛下比较三组方法：现有规则；字符 TF-IDF 或 BM25 配合规格约束；LightGBM 重排。

训练负样本从训练分区的实际召回候选中抽取，重点包括同型号不同容量、同容量不同地区版本、单件与套装、别名近似及字段缺失。维护随机负样本与困难负样本比例，固定实验预算，保留失败案例分类。评测集的无匹配占比若人为提高，应同时报告自然分布估计或多个占比场景，不将压力集覆盖率直接当作生产覆盖率。

校准前后 F1 相同，并不意味着校准没有价值；单调变换可能保留排序。新增 Brier 分数、固定分箱的 ECE 和可靠性曲线，结合样本量解释。只有在相同推荐精确率下覆盖率提升，或校准质量改善，才作相应收益声明。

语义向量召回放到第二轮：先统计召回漏失原因，确认为别名或描述差异时再引入，比较新增正确候选和新增规格冲突。交叉编码器、LLM 判定与多品类扩展暂缓。它们不能替代身份字段约束与完整流程评测。

## 4 产品与审核流程优化

### 4.1 将补资料变成可追踪的工作流

当前缺少任一关键身份字段都不能确认，需要修改完整文件并重新上传。该约束能防止猜测式确认，但少量问题也要求整表返工，影响实用性。

新增“待补资料”清单，展示缺失字段、冲突值、原始行号和处理原因，支持下载仅包含问题行的补数模板，以及在页面中填写更正值。更正保存为草稿；提交时生成新 Revision 和受影响记录的新运行，原始输入和旧结果保持可追溯。禁止直接覆写历史 Source.normalized。

补充字段必须记录值的来源、操作者和修改时间；不能自动用候选商品字段填补来源字段，再以二者一致作为匹配证据。高推荐、需补资料和规格冲突采用不同筛选入口；下一条待处理、快捷键和字段差异高亮可减少反复点击。

验收场景：1万行中20行缺字段，仅需处理这20行；错误原因能完整分页或下载，而不只显示前100条；更正后形成可追溯版本，不能绕过双人复核，旧导出仍能复现。

### 4.2 使用稳定来源身份比较版本

当前版本比较以“原始行号 + 来源编号”为键，文件重排会显示为新增和移除。应优先使用组织、供应商、批次业务范围内的稳定来源编号，将行号保留为定位信息。

来源编号缺失或重复时进入显式歧义流程。系统分配的行号编号不能自动视为跨文件稳定身份；内容指纹可用于提出对应建议，但修改字段、完全重复行或编号复用必须确认。供应商编号的唯一范围要在导入时校验，不能默认全组织唯一。

先完成只读差异比较，显示新增、移除、字段修改、候选变化和决定变化，再考虑跨版本复用。只有来源身份明确、身份字段未变、目标 SKU 有效且策略兼容时，才提示复用历史映射，并保留原决定来源；旧审核记录不直接迁移成新人工决定。

验收场景：随机重排同一文件，业务差异为零；修改5条记录的容量，仅这5条显示身份字段变化；重复或缺失编号进入歧义列表，不能静默覆盖记录。

### 4.3 导入异步化并复用映射

当前上传、预览和校验会重复解析文件；解析虽然有20MB、行列数和解压体积限制，仍在请求内执行。建议复用现有任务框架，建立 UPLOADED、PARSING、MAPPING_REQUIRED、VALIDATING、READY、FAILED 状态，保留已有文件限制与错误信息。

缓存键包含组织、文件哈希、编码、解析器版本；字段校验结果另绑定工作表、表头、映射和标准化规则版本。前50行预览与完整校验结果分开读取，错误列表分页。文件已安全保存后的建任务接口返回202并提供进度、失败原因与重试入口。

供应商映射模板保存列名对应关系和版本，遇到列缺失或表头变化需重新确认。验收同一解析配置不重复解析，重复提交不生成重复版本；异步期间能正常审核其他任务。建议文件保存后的任务受理 P95 低于1秒，文件上传网络耗时单列。

### 4.4 用试用结果决定下一轮界面调整

邀请2至3位采购、商品运营或熟悉表格核对的使用者，每人完成相近难度的50至100条数据处理。对照人工表格核对与平台流程，交叉安排使用顺序，减少熟练度影响。

记录完成时间、每条审核中位耗时、误确认、人工搜索次数、补资料往返次数和中断原因。建议争取总耗时降低30%，且误确认不增加；样本较小时只报告观察结果。无法找到业务人员时，可邀请同学做可用性试验，但不要表述为企业用户验证。

## 5 工程与运维优化

### 5.1 优先解决列表查询放大

源码中 items_list 对每条记录调用 item_data，后者逐条读取来源、候选、候选商品与审核事件；runs_list 对每个运行执行汇总查询；导出列表逐个计算变更计数。这是已确认的逐行查询结构，实际 SQL 数量和耗时占比仍需测量。29条数据上的 P95 747ms 值得优先分析，但不能只凭这一数字断言数据库是唯一瓶颈。

按当前页批量获取关联数据，使用 IN 查询、预加载或聚合连接；运行统计按一组 run_id 统一聚合。所有批量查询继续约束 org_id。列表返回摘要，候选详情按当前选中行加载；如需整页候选，统一批量查询，避免每行独立读取。

版本比较也存在逐行查询，应统一加载两次运行的首选候选并分页返回差异。目录、成员、批次和历史事件补齐搜索与游标分页，确保第101个批次及更早记录仍能找到。

验收先记录 SQL 数量与 EXPLAIN，再优化索引；目标每页核心业务查询不超过10条，页长从10增至100时查询数量基本恒定。使用真实 HTTP、PostgreSQL 和代理，在至少1万条任务记录、多个历史运行、10名并发用户下执行15分钟混合读取与审核；报告 P50/P95/P99、错误率、连接等待和 CPU/RSS。

建议列表 P95 低于500ms、审核提交 P95 低于300ms、非预期5xx低于0.1%。业务版本冲突单独统计。达不到时依据剖析结果继续优化，不预先引入 Elasticsearch 或拆分微服务。

### 5.2 补齐真实部署与故障恢复证据

验收报告明确说明 Docker、PostgreSQL、Redis、Celery、MinIO 组合未实际运行。需要在目标环境执行完整闭环，再验证真实依赖故障；SQLite 上的通过结果和 PostgreSQL DDL 生成成功不能替代这一步。

| 场景 | 应验证的行为 | 保留证据 |
| --- | --- | --- |
| 空环境部署与升级 | 迁移成功，登录至导出全流程完成 | 镜像版本、命令、日志、数据库版本 |
| Worker 被终止 | 自然租约到期后恢复，无重复有效结果 | 时间线、任务状态、结果计数 |
| Redis 中断与恢复 | 请求与发件箱状态可解释，恢复后补投 | 未投递数、延迟、重复消息结果 |
| 数据库或对象存储短暂不可用 | 操作明确失败或重试，不发布半成品 | 故障响应、事务与对象核验 |
| 旧 Worker 恢复提交 | 过期 fencing token 被拒绝 | 拒绝日志与唯一结果 |
| 双租户与并发审核 | 无越权数据，同一记录仅一个有效决定 | API 结果、约束与审核事件 |

自然恢复测试不人为修改租约到期时间。以现有120秒租约为基础，首轮建议恢复启动时间目标不超过180秒，并实测调度周期与排队影响；取消延迟另测。说明这是应用内数据不重复的验收，不将至少一次投递描述为消息恰好一次。

在明确的4核、16GB资源限制下重测1万 × 5万工作负载，报告索引构建、召回、打分、持久化的分段耗时，以及两个并发任务的内存总量。单任务775MB不能直接证明两个进程的总资源需求。

### 5.3 补充监控与数据生命周期

现有 metrics 主要提供运行状态数与过期租约数。优先补充队列等待时间、任务阶段耗时、发件箱最老未投递年龄、重试次数、租约回收、导入失败原因、审核版本冲突、API 延迟和对象存储错误。日志关联 request_id、run_id 和任务片段；监控标签避免按每条记录或原始商品名称展开。

初始告警可设置为：最老未投递事件超过5分钟、任务5分钟无心跳、10分钟内失败率超过5%。先通过故障演练校准，低流量时增加最小请求数条件。监控图表直接对应排查入口。

导出到期目前只阻止下载，需新增可重试的对象清理任务。数据库保留导出元数据、文件哈希和删除时间，物理对象在到期后24小时内清除。先统计对象引用，不能误删仍被模型、版本或有效导出引用的文件；“无引用”和“清理失败”应可观测。

恢复演练覆盖数据库、对象、模型、词表和必要配置，处理当前模型绝对路径依赖：使用稳定制品标识定位，恢复后验证哈希并重新关联路径。原库与对象备份须有一致性方案，可先暂停写入取得一致备份。每次恢复到新目录或新环境，验证跨租户数据、历史决定、模型加载和导出文件。生产 RPO/RTO 应在演练后制定，不能把已有本地备份成功当作生产指标达成。

## 6 分阶段交付与验收

### 第一阶段 建立可信基线

完成数据标注规范、冻结划分、端到端评测脚本和首批数据；统一打分特征生成；记录列表 SQL 与性能基线。交付数据清单、首轮完整流程报告、特征一致性结果和性能分析。数据效果不达标时保留模型实验状态，并明确最大的错误来源。

### 第二阶段 完成企业试用条件

完成列表批量查询、策略晋级校验和部署栈核心联调，执行真实 Worker 退出与依赖恢复实验。交付可复现部署命令、故障时间线、真实 HTTP 压测报告和策略发布清单。企业部署验收未通过前，展示中明确区分本地实现与已验证部署能力。

### 第三阶段 降低用户返工

完成补数模板或页面草稿、稳定来源身份比较、异步导入、分页与基础监控清理。进行小规模试用，记录任务耗时及错误。交付前后对照演示、试用问题清单和恢复报告。

### 第四阶段 以实验决定算法扩展

完成困难负样本实验，在相同精确率下比较规则和学习策略覆盖率。只有召回确有不足时再引入语义召回；只有重复供应商批次足够稳定时再加入历史映射建议；只有已有可靠人工反馈时再进行主动学习。每项扩展都需保留随机抽检，避免反馈只覆盖模型容易或不确定的样本。

对求职展示，最终应形成三组可核验材料：算法实验展示数据划分、困难负例、消融及精度覆盖率权衡；企业工程展示幂等、租户隔离、真实故障恢复与版本可追溯；产品价值展示补数与审核耗时的实际变化。简历中的性能数字注明环境与数据规模，模拟数据和公开基准不写成真实客户上线成果。
