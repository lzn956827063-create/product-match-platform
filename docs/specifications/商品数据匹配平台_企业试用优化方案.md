# 商品数据匹配平台企业试用优化方案

方案版本 1.0　实施基线 产品 v1.1　编制日期 2026年9月10日

本方案将商品数据匹配平台从本地可运行的优化版本，推进到可供企业小范围试用的业务系统。第一阶段优先完成全量有效映射发布、多人审核协作以及真实部署验收；第二阶段补充标准库变更影响、下游系统对接和数据质量管理；算法改进以独立标注和可复现实验为依据。

方案面向项目开发者与验收人员，包含功能范围、关键技术设计、实施依赖和验收条件。“企业级”在这里指能够在约定的规模与环境下可靠地完成业务交付、支持多人操作、追溯责任并从故障恢复，不代表通用认证或任意规模的生产承诺。

## 1 当前基础与本轮目标

### 1.1 现有能力

v1.1 已完成异步导入、映射模板、补数草稿、稳定来源编号比较、列表批量查询、冻结学习流水线、完整策略评测绑定、影子对照和基础运行监控。后续开发应复用现有租户隔离、幂等、乐观锁、任务租约、发件箱和不可变历史设计。

最新交付报告记录55项后端测试及24个浏览器检查点通过。本地真实 HTTP 负载中，摘要列表 P95 为109.7ms，审核提交 P95 为93.0ms；自然租约恢复用时120.88秒。这些是交付报告已有结果，本方案没有重新执行测试或生产部署。

| 当前边界 | 业务影响 | 本轮处理方向 |
| --- | --- | --- |
| 补数只形成子集运行和子集导出 | 用户仍需合并原结果与补数结果 | 建立全量结果及发布快照 |
| 审核有版本冲突保护 | 能防止覆盖，仍可能重复投入审核时间 | 分派、领取和转交 |
| 部署组合尚未实际联调 | 生产依赖故障行为没有现场证据 | 完整部署与真实故障演练 |
| 新接口压测仅12件标准商品 | 不能证明5万标准商品及多任务容量 | 目标环境混合负载测试 |
| 模拟集三种方法效果相同 | 尚未证明学习算法优于规则 | 独立标注及主动学习实验 |

### 1.2 试用范围

第一阶段限定手机 SKU、人工必审、单个企业或少量组织的受控试用。初始验收负载为每批最多1万条来源、标准库最多5万条商品、10名并发操作用户，以及两个组织同时有后台任务。生产式测试使用 PostgreSQL、Redis、Celery、MinIO 和反向代理，建议以4核、16GB作为第一组明确的资源预算；负载不达标时调整容量或资源，不挪用本地数字作为通过证据。

单机部署可作为首轮试用形态，应说明其停机与恢复边界。跨机高可用、灾备和更高并发属于后续独立容量目标。学习模型未通过业务准入时，规则策略与人工审核仍可承担试用流程。

P0 是进入本轮受控企业试用前的必做项；P1 是接入实际业务链路前或试用期间完成的增强项；P2 由客户环境与实验结果决定。编号表示功能或工程任务，优先级表示交付顺序。

## 3 全量有效映射与发布中心

### 3.1 用户流程

业务人员打开批次后，应看到当前全量处理结果及未解决问题。完成原任务审核和补数复核后，创建发布草稿，查看发布范围、差异及阻断项，通过校验后发布，得到固定版本的全量文件及增量变更文件。

例如原表1万条、修正20条，用户只处理这20条补数；发布仍覆盖原来的1万条来源。每条发布记录注明已匹配、确认无匹配或排除等状态，不能将未处理记录伪装成已完成。提供“完整核对结果”和“仅有效映射”两种导出时，必须分别显示行数和筛选范围。

补数子集导出继续保留，但页面应优先引导用户使用批次发布版本进行正式交付。原有运行、审核事件和历史导出保持原始含义。

### 3.2 结果解析规则

为来源记录建立稳定的业务身份，并保留父子修正关系。来源编号只在明确的组织、供应商和批次范围内使用；编号缺失、重复或复用需要人工消歧。补数关系优先依据已有父记录链接，不依赖文件行号推断。

全量结果从选定完整基线及明确选定的补数分支解析。修正已提交但尚未审核、已撤销、存在两个未合并修正分支时，发布检查显示阻断原因。仅保存在个人草稿中的改动不进入结果解析，但可显示未提交提醒。不能按更新时间直接选择一条，也不能在新修正无效时静默退回旧映射。

未发生身份变化的记录可以引用原有效审核事件及其来源版本，不创建“新的人工审核”记录。被修正的记录必须引用新审核事件。下一份完整输入文件有新增或移除记录时，显式确认范围变化；不得将补数子集误认为完整替换文件。

### 3.3 发布与并发控制

建议发布状态采用 DRAFT、VALIDATING、READY、PUBLISHED、SUPERSEDED 和 REVOKED。草稿内容改变后必须重新校验；PUBLISHED 内容不可修改，变更创建新版本。新版本替代旧版本与主动撤销是不同事件，需分别记录。

发布清单冻结来源范围、决定引用、标准库版本、策略版本、各状态数量与内容哈希。基于批次结果版本或逐项版本校验，保证校验至发布之间的决定变更被发现；存在变化时重新校验。大批次可先异步生成快照，再在短事务内核对版本并切换发布状态，避免长时间锁住整批数据。

数据快照发布与文件生成状态分开：发布完成后文件可处于生成中，下载在文件完成并校验哈希前不可用；下游交付事件只在所需制品就绪后投递。重复发布请求通过幂等键返回同一结果，不产生重复版本。

建议新增 BatchRelease、ReleaseRow 和 ReleaseEvent。ReleaseRow 保存稳定来源身份、结果状态、决定引用、来源版本、目标 SKU 及必要快照字段；所有关联携带 org_id。已经发布后发现决定撤销，应生成发布失效或撤销事件并提示下游，不修改旧文件字节内容。

### 3.4 验收场景

- F1-01：1万条原记录加20条补数，完整发布仍为1万条且没有重复来源；20条引用新决定，其余保留可核验的原决定引用。
- F1-02：未审核补数、撤销决定或分支冲突阻断发布，页面定位到具体问题；草稿不被当作已提交结果。
- F1-03：发布校验期间修改一条决定，旧校验不能直接发布；并发提交仅生成一个指定版本。
- F1-04：新完整版本删除5条记录时，增量结果有5条删除或失效事件；补数运行不产生整批删除。
- F1-05：发布后重试文件生成、重复下载与旧版本查看均能核对相同快照哈希；跨组织不可访问。

## 4 多人审核与商品变更管理

### 4.1 审核分派与领取

主管按批次、供应商或问题类型分派任务；审核员进入“我的待办”领取记录，查看原文与候选后提交决定。列表展示分派人、持有人、待处理时长和超时状态，支持退回、转交及下一条。

分派用于表达责任，领取用于表达当前操作占用，二者分开建模。新增 ReviewAssignment 和 ReviewClaim，领取状态可为 AVAILABLE、CLAIMED、COMPLETED、RELEASED 或 EXPIRED。采用数据库原子条件更新或行锁领取；领取有短期租约与 claim_token，续期、释放、提交决定均校验身份和 token。

首轮可使用5分钟领取期限、每分钟续期，作为可配置初值。浏览器关闭或断网后允许到期重新领取；主管强制转交需记录原因。claim_token 解决过期持有人问题，expected_version 继续解决业务版本冲突，不能以领取取代原有乐观锁。

权限扩展为审核主管、审核员与发布者，可组合授予。开启双人复核的批次，提交者仍不得审核自己的记录；主管权限不自动绕过该规则。批量确认按集合校验领取资格和版本，并返回逐项成功或失败结果。

验收：20次并发领取同一记录仅一个成功；租约过期后新领取人可处理，旧 token 被拒绝；分派、转交、退回均有事件；跨组织和提交者自审被拒绝；重复提交不重复生成有效决定。

### 4.2 标准库变更影响分析

标准库新版本先生成新增、停用、身份字段变化和非身份字段变化清单，再查找受影响的有效映射、批次及发布版本。明确商品稳定标识与版本记录标识，SKU 编码改名、编码复用不能仅凭字符串相同建立对应。

身份字段变化或 SKU 停用触发重新匹配、人工复核或替代商品确认；单纯展示名称变化在规则明确的条件下可只通知。替代商品建议不能自动覆盖旧映射。历史发布继续绑定原标准库版本，当前工作结果显示需要处理的影响。

建议新增 CatalogChange 与 ImpactTask，并在 Mapping、ReleaseRow 的商品引用上维护可查询索引。影响分析以目录版本对为输入，异步执行并保存统计；标准库发布人看到影响摘要，决定何时切换新任务默认版本。

验收：修改10个 SKU 时，准确列出引用它们的有效映射和发布版本，不将无关记录加入复核；停用商品不能用于新正式发布；旧版本仍能解释历史依据；重复执行影响任务不重复创建待办。

## 5 系统对接与供应商质量管理

### 5.1 交付任务与下游回执

提供服务账号、发布版本查询、增量变更查询、交付任务和回执接口。服务账号绑定组织及最小权限，支持凭据轮换、到期、停用与访问审计；不使用管理员个人登录令牌执行长期对接。

推荐流程为：发布制品就绪后，在业务事务中写发件箱事件；后台发送通知；下游按 release_id 获取快照或增量，处理后提交回执；平台展示接收、处理成功、部分失败或需要人工处理。HTTP 2xx 只表示通知被接收，业务处理成功以回执为准。

建议新增 Integration、Delivery 和 DeliveryAttempt，交付记录包含组织、发布版本、事件编号、目标、尝试次数、下次重试、最后错误及回执。对端凭事件编号幂等处理。Webhooks 采用带时间戳的签名，校验允许时间窗口并防重放；目标地址由管理员配置并限制出站访问，避免任意用户地址触发内部网络请求。

采用指数退避和抖动重试，达到上限进入人工重放队列。重放保留原业务事件编号及新尝试编号。增量必须基于明确的基线发布版本，包含 upsert、delete 或 invalidate 语义；接收方缺少基线时转为全量同步。撤销已交付发布时另发撤销或失效事件，并跟踪对端回执。

无真实 ERP 时，先建设模拟采购接收端，实现同样的权限、幂等、故障及回执协议。模拟通过只证明集成协议和本项目行为，不描述为真实 ERP 已接入。

验收：同一事件发送10次，下游仅应用一次；下游暂时不可用后可重试成功；部分记录失败能够定位并补偿；撤销通知可追踪；服务账号跨组织读取、超范围操作及过期凭据被拒绝。

### 5.2 供应商数据质量中心

先增加稳定 Supplier 实体，将现有文本供应商名称映射为业务身份；同名或历史别名由管理员确认，不能直接聚合为同一供应商。映射模板、批次、质量统计和权限范围逐步绑定 supplier_id。

质量面板展示关键字段缺失率、来源编号重复率、内部规格冲突率、首次完整审核完成率、补数往返次数和处理时长。每个指标显示分母、统计周期、数据版本及下钻明细，区分导入时质量、修正后质量和匹配效果。

无匹配可能是标准库覆盖不足，不直接算供应商错误；不同品类、规模与字段要求的供应商不能用一个混合分数排名。首轮提供分项趋势与待改善清单，暂不建立不透明综合评分。

验收：同一测试批次的面板指标可用原始行逐项复算；补数后可同时查看前后质量；重复导入和重复事件不重复计数；小样本结果展示样本量，不作稳定排名。

## 6 标注工作台与算法迭代

### 6.1 从审核反馈建立可信标签

工作台收集人工改选、无候选、规则与模型分歧、规格冲突及随机高推荐抽检。审核事件只是候选标注证据，不能未经复核直接当作训练真值。人工选择本身可能受到模型推荐影响，应保留选择来源和展示策略版本。

新增 AnnotationTask、AnnotationDecision、DatasetVersion 和 SamplingRound。两名标注者独立判断同一 SKU、不匹配或资料不足；资料不足单独保留，不能转换为负例。分歧进入裁决；标注者、裁决者和规则版本可追溯。评价集冻结后不可由日常训练反馈覆盖。

来源数据分为获得授权的目标领域记录、公开基准和受控模拟数据，分别报告。没有真实授权数据时可以完成标注工具和模拟实验，但学习策略继续保持实验资格，不能用工具功能替代业务数据证据。

### 6.2 固定预算比较主动学习

先固定实体级训练、验证和测试划分，近重复及别名随实体分组。训练池每轮选样比较随机抽样、模型不确定性、规则与模型分歧三种策略，各分支使用相同初始标签、样本预算和独立训练流程。选样仅访问训练池，测试标签不参与选择。

可从每轮100个候选对、3至5轮开始，按资源调整。各策略保留一部分随机样本，兼顾错误发现和样本覆盖。预算同时记录候选对数、独立实体数和实际标注分钟数；难例更耗时，不能只用条数判断效率。

主指标为相同推荐精确率约束下的覆盖率；辅助指标包括 Recall@20、端到端推荐召回、无匹配误推荐率、Brier/ECE、标注耗时和错误类型。固定训练预算并进行多随机种子实验，报告实体分组区间。实验过程用验证集决策，最终冻结方案后才对测试集评估，避免多轮挑选测试最好结果。

### 6.3 按错误类型选择算法

| 观察到的主要问题 | 优先方法 | 必须比较的结果 |
| --- | --- | --- |
| 别名或描述差异造成漏召回 | 字符召回与语义召回融合 | 固定候选预算下的召回、冲突率及耗时 |
| 正确候选在列表中但排序靠后 | 困难负样本与 LightGBM 重排 | 相同推荐精度下的覆盖率 |
| 关键身份字段缺失 | 资料获取或有出处的字段提取 | 字段精确率、拒答率及人工修正成本 |
| 相同供应商重复上报 | 满足版本条件的历史映射建议 | 建议正确率、失效检测与审核节省 |

当前模拟集的三种方法效果相同，先扩大数据难度与独立性。语义模型、交叉编码器或 LLM 只在相应错误占比证明其价值后引入；身份硬冲突与缺资料规则继续生效。字段提取不得用候选商品的属性补造来源证据。

业务学习策略沿用已有完整策略准入。建议高推荐精确率点估计至少98%，同时报告区间与独立推荐实体数；Recall@20 初始目标至少95%，无匹配误推荐点估计不高于1%。样本不足或区间不支持声明时保持探索性结果。规则人工流程的试用不依赖学习策略必须胜出。

## 7 企业运行与工程验收

### 7.1 真实部署与故障演练

在隔离环境实际启动 PostgreSQL、Redis、Celery、MinIO、API 和代理，完成空库迁移、登录、导入、匹配、审核、补数、发布和交付。启动探针应区分进程存活、依赖就绪及服务降级，明确依赖失败时哪些操作仍可受理。

| 演练场景 | 关键验收行为 | 证据 |
| --- | --- | --- |
| Celery Worker 被终止 | 自然租约到期后恢复，旧 token 无法提交 | 真实进程与任务时间线 |
| Redis 中断并恢复 | 发件箱持久保存，恢复补投，不重复业务结果 | 队列与发件箱状态 |
| PostgreSQL 短暂中断 | 事务边界明确，不生成半份审核或发布 | API响应、事务与重试日志 |
| MinIO 不可用 | 文件未完成前不可下载或交付，恢复后可重试 | 文件状态、哈希与对象核验 |
| 发布时并发撤销 | 发布版本检查识别变化，或后续生成失效事件 | 快照、决定和事件顺序 |
| 重复交付及下游中断 | 幂等应用、重试和回执状态一致 | 两端事件与回执记录 |

自然租约测试不得人为修改到期时间。首轮以现有120秒租约为基础，建议180秒内开始恢复执行，报告排队影响。应用内有效结果不重复与消息只投递一次分开表述。

### 7.2 容量与组织公平性

使用5万标准商品、每批1万来源、多历史版本和两个组织构建负载。数据同时包含完整记录、缺字段、近似型号、冲突和无匹配，不仅复制少数商品。分开报告 API 负载与后台匹配负载，再测二者混合运行。

记录列表、候选详情、审核、发布校验、搜索和下载的 P50/P95/P99、错误率及吞吐；记录索引构建、召回、打分、持久化分段耗时，以及数据库连接等待、锁等待、API与全部 Worker总内存和对象存储量。

首轮建议10名并发用户下列表 P95 不高于500ms、审核提交 P95 不高于300ms，非预期5xx或网络错误低于0.1%；版本冲突和限流响应单独统计。按约定请求节奏运行至少30分钟，报告冷启动与稳定阶段。总任务完成时间先测量形成基线，再确定目标，不直接继承旧机器的93.39秒。

在已有组织并发限制上增加排队上限、文件与存储配额、API限流以及明确的超额提示。调度采用按组织轮转或权重公平策略；长匹配任务与短导入、导出任务设置可配置的资源分配，避免单一组织长期占用全部执行槽位。

验收一个组织持续提交大任务时，另一个组织仍可正常审核；当轮到其任务且执行槽位可用时，在一个约定调度周期内获得调度机会。配额预占、扣减与释放在重试和取消后保持一致，不能因重复请求重复消耗。

### 7.3 监控与运行责任

将现有指标接入 Prometheus 与 Grafana，按每个 API/Worker 实例采集并聚合；进程内指标重启清零，不将单个实例统计当作全服务统计。持久队列与业务状态由数据库查询提供，避免指标标签包含来源记录或敏感原文。

面板至少覆盖接口延迟与错误、队列最老等待、任务阶段、租约恢复、发件箱积压、发布与交付失败、对象清理、磁盘及连接池。告警包含最小样本数与持续时间，关联 run_id、release_id 或 delivery_id 的排查入口。监控使用专用最小权限身份或受控内部采集入口。

上线前完成一次“告警触发到定位并恢复”的演练，记录负责人、告警渠道、升级路径和处理步骤。建议以30天服务可用性99.5%作为首轮讨论目标，须定义测量接口、统计范围及维护窗口；短期测试不能宣称已达到月度可用性。

### 7.4 升级与备份恢复

CI 应运行现有核心回归及新增发布、领取、交付测试，在 PostgreSQL 上执行迁移与关键事务验证，并保存构建版本、依赖锁与制品哈希。镜像上线前核对配置和数据库版本，先在预发布环境升级旧版本样本数据。

数据库变更优先采用兼容旧应用的新增字段、回填和延后清理顺序；应用回退不默认等于数据库可以降级。失败处理要事先明确选择应用回退、向前修复或从备份恢复，避免上线后临时决定。

备份覆盖数据库、对象、模型、冻结词表、评测清单与必要密钥配置，确保快照引用一致。每次恢复到独立环境并验证跨组织隔离、历史决定、发布文件、模型哈希及待交付状态。交付重试须先与下游对账，避免恢复后重放已经生效但回执丢失的事件。

第一轮可将 RPO 不超过24小时、RTO 不超过2小时作为待验证的试用目标，并告知可能的数据损失窗口；业务不能接受时需缩短备份间隔或引入日志归档等机制。只有恢复演练通过后才能声明该配置达到目标，单机备份不等同于高可用。

### 7.5 按实际客户环境增加身份能力

企业内部部署可优先接入 OIDC，按稳定身份标识绑定用户，校验组织成员资格；企业身份源停权后，按约定时限使本地会话失效。身份源账户与本地应急管理员分开管理并审计。SAML、SCIM 或更复杂权限层级在目标客户明确需要时再实现。

已有操作、审核、管理员角色继续保留，按发布、分派、集成管理等新增动作补权限矩阵。权限要在 API 与任务执行端校验，不能只依赖按钮隐藏。正式部署凭据、演示账号和模拟数据应使用独立配置与环境。

## 8 分阶段实施与完成条件

### 第一阶段 完成发布及试用运行基础

预计4至6周，交付 F1、F2、E1、E2。先确定来源身份、修正分支与发布规则，再实现快照和文件；领取机制与部署联调可在互不依赖的开发时段推进。最后在生产式部署运行完整用户流程及故障演练。

进入受控试用的门槛：正式结果能完整发布且可追溯，多人操作不重复覆盖；目标环境核心流程通过；备份恢复和至少一次 Worker/依赖故障演练通过；容量目标有实测证据，未通过项明确限制使用范围。学习模型不达标时使用规则及人工审核。

### 第二阶段 完成业务交付链路

预计再投入2至4周，交付 F3、F4、E3，并按余量加入 F5。先有稳定发布版本，再实现增量交付；先有标准商品身份对应，再做影响分析；供应商质量聚合依赖 Supplier 身份迁移。

完成条件：下游能够确认实际应用结果，重复通知不会重复生效，撤销和增量可对账；商品变化能定位需要复核的记录；组织资源滥用不阻断其他组织的基本业务。

### 第三阶段 验证业务收益与算法改进

预计再投入2至3周开发与实验时间，数据授权、标注和招募等待另计。完成 A1，并邀请2至3名业务相关人员执行交叉顺序的表格核对与平台任务，记录总耗时、误确认、补数往返和交付问题。

试用可初步争取总耗时减少30%，但必须使用相近难度样本并报告人数和条数；没有真实参与者时不填写收益。主动学习实验无提升时保留负结果，分析数据分布与选样成本，不强行发布新模型。
