# 商品数据匹配平台成熟度评估与优化方案

评估基线 产品 v1.2　建议下一版本 v1.3　编制日期 2026年9月10日

v1.2 已形成具有企业业务特征的完整原型，能够在本地完成导入、多人审核、补数合并、完整发布、模拟系统交付和追溯。当前尚未达到已验证的企业生产使用标准；按上一版方案的准入条件，目标环境下的受控企业现场试用验收也未完成。

下一轮建议从功能扩展转向业务闭环完善、真实部署验证、大数据量性能和真实用户试用。重点是关闭交付长时间无回执、发布影响待办关联校验、大库变更分析和全量重复计算等具体问题。已有发布中心、审核协作、质量中心和标注工作台继续深化，不重新建设同类模块。

本评估依据最新使用说明、验收报告、运行文档和相关源码静态核对。已有测试及性能数字引用交付报告；本次没有重跑完整测试、启动生产栈或修改项目代码。文中区分报告已有证据、静态代码发现和建议验收目标，建议值不代表已达成。

## 1 是否达到企业级标准

### 1.1 分层判断

| 使用层级 | 当前判断 | 判断依据 |
| --- | --- | --- |
| 本地演示与开发验证 | 已具备，报告有较完整证据 | 75项核心测试、37项浏览器检查；本地完整流程与协议演练 |
| 企业业务功能完整性 | 已形成较完整基础 | 发布、协作、标准库影响、交付回执、质量与标注均已实现 |
| 受控企业现场试用 | 尚未通过准入 | 目标依赖栈、真实用户流程、现场监控与恢复仍未验证 |
| 企业生产运行 | 不能判定达标 | 真实部署、持续容量、运行责任和服务目标缺少执行证据 |
| 学习模型业务准入 | 未通过，实验状态合理 | 受控模拟数据上三种选样策略无收益，没有真实标注参与者 |

“具有企业功能”与“已验证可以企业生产运行”是不同结论。企业级能力要对应明确的用户、规模、部署方式、恢复目标和业务责任。OIDC 或高可用不是所有企业试用的统一前置条件；需要时按客户要求补齐，不能将它们作为当前未达标的唯一理由。

### 1.2 本轮已有证据与限制

报告记录：两组织各5万标准商品、1万来源，10名模拟用户，真实 TCP 负载运行1801.21秒，共17849次请求，约9.91请求每秒，非预期5xx或网络错误为0。来源列表 P95 为140.00ms，审核提交 P95 为56.46ms；标准库搜索 P95 为889.26ms，P99 为1650.86ms。审核 P99 为1004.52ms，说明少量请求仍明显慢于多数请求。

测试采用本机8逻辑CPU、16GiB、SQLite WAL与本地调度器，无容器限额、PostgreSQL、Redis、Celery、MinIO或代理。两项后台任务只在初期各运行一次；未覆盖持续后台饱和、正式发布校验和下载混合负载，也未保存逐请求延迟。测试后还有代码调整，因此不能将该报告当作最终制品完整容量验收。

真实本地 Worker 被终止后，120.61秒观察到自然租约恢复。备份恢复核验包含34个文件、15个发布制品、121条审核历史和1条待交付通知。这证明本地实现已有恢复机制，不能替代 PostgreSQL、MinIO、Celery 组合下的恢复结论。

### 2.2 如何表达项目价值

目前可以准确描述为“已实现商品核对从导入到完整发布和模拟采购交付的可追溯流程”。最突出的业务价值是完整结果交付、多人审核责任明确，以及标准商品变化后的风险定位。

现在还不能宣称“企业已上线”“真实准确率100%”“减少30%人工成本”或“达到月可用性99.5%”。界面存在不等于用户任务完成，自动化测试通过不等于真人工作量下降。下一轮将以实际完成时间、错误、返工次数及最终下游状态验证这些收益。

## 3 本次静态核对的新发现

### 3.1 发布影响待办的关闭关联不足

apps/api/enterprise.py 的 impact_resolve 已检查替代记录使用新标准库且经过审核。对 item_id 类型待办，还检查相同输入版本及来源记录；对只有 release_id 的发布类型待办，没有同等的批次、受影响来源和替代发布关联检查。

按当前条件，发布类型待办可能引用同组织、同新标准库下不相关的已审核记录后被标记 RESOLVED。该结论来自静态条件核对，尚未运行请求复现；影响首先是待办处理状态的可信度，不能据此断言发布资格或旧文件也会被绕过。

建议列为P0修正：发布影响处理必须绑定原发布、受影响来源集合以及新的发布或明确的撤销处置证据。条目复核完成与整份发布处置完成分开记录，不用一个任意 replacement_item_id 代表整份发布已处理。

### 3.2 已接收通知缺少回执超时闭环

workers/deliveries.py 将通知2xx置为 RECEIVED 并完成对应发件箱；后续处理遇到 RECEIVED 会直接返回。当前有人工重放入口，但未找到回执截止时间及超时扫描处理。

这意味着接收方通知成功后未回传业务结果时，交付可长期停在 RECEIVED，依赖人工查看。它不等于数据已经丢失，但业务人员无法仅凭该状态判断是否需要处理，应增加对账与超时升级流程。

### 3.3 大库变更分析存在平方级遍历

workers/catalog_changes.py 第25行起，对每个新商品执行“是否在 job.links.values() 中”的检查。字典值视图的成员检查为线性遍历，嵌套后接近 O(N×M)。两侧与对应关系都达到5万规模时，比较次数量级可达十亿，实际耗时尚未测量。

同一处理函数在写事务内锁定组织并执行身份绑定和影响计算，可能扩大同组织并发操作的等待，需要在 PostgreSQL 上验证。页面使用虚拟列表，但 identity-index 仍一次读取最多5万条记录，且前端同时加载两个版本；虚拟渲染本身不减少网络传输和内存占用。

### 3.4 分页返回仍有全量重复计算

service_delta 每次分页都读取两个完整发布并重新计算差异；quality_detail 每页都读取完整来源和审核事件、重建全部问题后切片。supplier_quality 最多按时间顺序返回100个输入版本，没有继续翻页的游标；较长周期可能只展示前100个版本。

这些接口在小数据中能正常工作，但随着发布、版本和审核历史积累，会增加重复计算或遗漏范围的使用风险。建议持久化不可变差异与质量问题明细，补齐完整分页和统计范围说明。

### 3.5 搜索与尾延迟有实测改进空间

标准库搜索使用 SKU、JSON名称和型号上的包含匹配条件，已有报告中搜索 P95 约889ms。SQL结构说明了应重点剖析的路径，但尚不能仅凭源码确定慢查询的唯一原因。

列表和审核 P95 已较好，下一步应分析 P99 与数据库连接等待、锁等待、后台提交的相关性，而不是继续只优化平均值或报告更大的总请求数。

### 3.6 影响处理页面与耗时口径还需补全

CatalogImpact.vue 已提供查看受影响记录，但当前组件未提供调用 resolve 接口的完成操作，发布类型待办也没有与新发布处置连贯的页面入口。后端接口已存在，不应把它误写为整个功能缺失；应补齐用户能完成的操作路径。

质量统计中的 completed_processing_seconds 从来源创建到最后完成审核，包含排队、等待补资料和人工操作；它适合表示处理历时，不能当作人工净工作时间。若用于收益评估，应另外采集有效操作时长和等待时间。

## 5 关键功能完善方案

### 5.1 发布影响处置闭环

将影响处理分为“记录复核”和“发布处置”。记录复核绑定同一稳定来源及新标准库下的审核事件；发布处置绑定原发布、受影响 stable_key 集合、新发布版本或撤销事件，并验证相关来源已覆盖。新发布未就绪或缺少处置依据时不可关闭。

一个商品可能对应发布中的多条来源，不能用一条审核记录替代整个集合的确认。处置还应区分需要业务复核、已生成替代发布、下游待确认和已完成；先解决平台内影响，再跟踪交付结果，避免一次勾选代表所有环节结束。

前端增加“处理影响”入口，展示旧依据、待复核范围、可选新运行及发布。对补数来源通过稳定身份及父子关系验证，不要求用户通过非关联记录绕过现有接口限制。提供完成前检查及缺项原因，保留处置人、时间和理由。

验收：不相关批次、来源、新库或未审核记录全部拒绝；两条受影响来源只修正一条不能标记整份发布完成；并发关闭幂等；新发布后下游尚未确认时状态明确；旧发布文件仍能核对原哈希。

### 5.2 交付回执超时与对账

在通知接收后保存 received_at、receipt_due_at、最后查询时间和升级状态。截止时间由集成配置决定，首轮可设15分钟为默认值并允许按下游处理时长调整。超时进入“待对账”，显示负责人和下一步，不直接标记失败或重复应用数据。

有对端查询接口时优先按 event_id 主动查询；没有查询能力时进入人工对账或按约定发送回执提醒。迟到回执校验事件和处理版本，并通过 token 或业务版本处理与人工重放的竞争。原业务事件编号保持不变，通知尝试另有编号。

增量接收端需持久保存当前基线、已处理事件、应用结果和回执。基线不符时拒绝增量并请求全量；按明确的发布版本顺序处理，旧版本迟到不覆盖新版本。已有模拟端含版本号保护，应新增乱序验证而不是重复建设该逻辑。

分页增量应先进入暂存区，验证完整性后原子切换可见版本，或明确提供下游可接受的逐条处理语义。删除、失效、部分失败、撤销与重复通知都要参与测试。回执除事件号外可增加实际应用发布、基线和摘要，但接收方声明不能替代实际对账。

验收：通知2xx后不发回执，截止后一个扫描周期内生成待办；迟到回执不重复应用；先收到新版再收到旧版不会回退；增量处理前后与全量结果一致；中途断线或部分失败后重试不重复删除和写入。

### 5.3 统一待办与资料回收

将现有发布阻断、待补资料、标准库影响和交付异常汇入一个按责任人过滤的待办入口。各业务模块继续保存自己的状态和权限；统一入口仅聚合、分派和导航，不另建相互矛盾的状态机。

列表显示业务对象、原因、等待时长、责任人和下一步。优先增加“打开后可以完成”的路径，避免只有统计卡片。明确主管可以转交但不能自动获得审核权，发布者也不能绕过双人复核。

供应商资料回收先采用现有问题模板的批量回导：模板包含固定问题编号、来源身份和原版本；回传后只形成补数草稿，校验重复、未知编号及旧版本，并要求数据专员确认后提交。此阶段不必增加面向外部用户的供应商门户。

验收：20条问题下载后回填，能准确生成20条草稿；乱序回传不串行，旧模板和重复导入有明确结果；业务人员可以从待办完成补数、发布影响处置和回执对账，无需调用API或修改数据库。

## 6 性能与数据规模优化

### 6.1 大库影响分析

首先将已对应目标商品ID构建为 set，消除对 values 的重复线性检查；加入1千、1万、5万规模的独立耗时记录，检查增长趋势。不能因一次 set 优化就宣称整个流程为线性，数据库读写和影响引用查询需分别测量。

把身份建议生成和全量变更计算转为后台任务，前端只分页读取待确认项和冲突。按规则一致、改名、字段变化、未对应分组展示，支持带依据的批量确认。提交前显式确认停用数量，避免未加载或漏操作的记录被当作停用。

以版本哈希或结果版本固定分析输入，在短事务内发布分析结果。长计算阶段尽量不持有组织级写锁；缩小锁范围前补齐并发身份绑定、重复任务、标准库切换和失败重试测试，不直接删除现有一致性保护。

验收5万对5万商品、至少10个历史发布引用的场景：影响集合正确，重复分析不重复待办；批次审核在后台分析时仍满足约定延迟；首屏仅传一页数据；提交后有进度和失败恢复。首次确定总时长基线，之后依据业务要求定上限。

### 6.2 搜索与数据库等待

保存慢请求 trace_id，并关联SQL执行、连接池等待、锁等待、JSON序列化及响应体大小。先在 PostgreSQL 执行实际参数下的 EXPLAIN ANALYZE，再决定索引和查询改写。区分无条件列表、精确SKU、型号前缀及名称模糊搜索。

建议将常用搜索字段规范化为可索引列，SKU精确查询优先走组织、版本和SKU索引；包含匹配可评估 pg_trgm 与GIN索引。中文短词及短型号要单测，不能假设所有查询都会使用三元组索引。前端可防抖并取消过时搜索请求，但不以此掩盖后端慢查询。

目标环境混合负载建议：列表 P95≤500ms、审核 P95≤300ms、搜索 P95≤500ms；列表及审核 P99初始争取≤1000ms，搜索 P99≤1500ms，非预期5xx/网络错误<0.1%。这些是本轮建议目标，须固定资源、数据、请求节奏和统计区间后验收。

### 6.3 差异和质量计算物化

已发布快照不可变，可在发布后一次性生成相对固定基线的 ReleaseDelta 明细，按发布版本与序号分页。缓存或物化键绑定组织、基线、目标版本和算法版本，避免每100条重新计算两份全量数据。基线不同仍按现有约定要求全量同步。

输入缺字段、重复与内部冲突可在校验后生成质量快照及问题行表；审核相关质量随事件更新，或按明确的审核版本异步重算。显示统计生成时间和覆盖范围，不将过期指标伪装成实时指标。

供应商质量列表增加游标及完整周期汇总，去除“仅前100版本却看似整个周期”的歧义。补数轮数区分直接子版本数、最长修正链和累计补数次数，明确重复内容处理口径。

验收：跨200个输入版本仍能完整查看；翻页读取量随页长有界；同一差异只计算一次或命中固定缓存；决定撤销后审核质量刷新；报告总数与逐版本结果可复算，跨组织缓存不共享。

## 8 实际业务价值与算法验证

### 8.1 真实用户完成任务

邀请2至3位采购、商品运营或熟悉商品表核对的业务人员，在相近难度的记录集上分别使用表格和平台，交叉安排顺序。以50至100条来源及10至20条问题作为首轮可控任务，另单独验证大批次功能，不把小样本效率当作容量结果。

任务覆盖导入、识别冲突、补资料、确认无匹配、完整发布，以及查看回执。观察是否需要开发者解释、调用API或线下拼文件；每一次中断都记录原因，并据此优先修复操作闭环。

| 业务指标 | 测量方式 | 第一轮判断原则 |
| --- | --- | --- |
| 人工有效操作时间 | 前台活跃区间结合观察记录，排除长时间离开 | 对照表格流程，报告样本及差异 |
| 端到端历时 | 开始至完整发布或下游应用 | 与排队、补资料等待分开 |
| 错误与返工 | 独立复核真值、记录误配和发布回退 | 时间减少不能以错误增加换取 |
| 无辅助完成率 | 无开发者介入完成的参与者与任务数 | 暴露界面和权限断点 |
| 下游一致性 | 发布版本、行数、映射摘要及对端状态 | 确认交付到达并实际应用 |

“节省30%时间”保留为探索目标，不是事先保证。展示配对任务的实际结果和个体差异；人数少时不推断所有企业。没有参与者时提交空白采集模板与招募依赖，不能用自动化模拟用户填补。

### 8.2 算法先处理真实错误

本轮主动学习9个最终分支均持平，受控集覆盖率60.56%，没有学习收益。这是应保留的实验结论，继续在同样的构造分布上调参或换更大模型很难增加说服力。

优先获得可使用的目标领域商品记录，保留来源及字段依据，按实体和近重复分组进行独立标注。候选对标签不足以证明完整检索真值；评价全库召回时，确认查询对应的全部在库关系，无匹配样本也需核验不能在库中找到其他等价记录。

第一轮统计漏召回、候选排序错误、规格提取错误、缺资料和标准库覆盖不足的占比，再决定投入。对于简称与噪声优先改进检索；对于候选已有但排错优先困难负例；对于缺字段优先资料回收。每项改动在相同候选预算与精度约束下比较覆盖率、耗时及人工纠错。

训练、验证及测试冻结，近重复组不能跨分区；模型准入沿用现有资格和完整策略校验，不降低门槛以获得“可用”标签。真实标签不足时继续使用规则及人工审核，并将算法能力展示为可信的数据划分、错误分析和负结果解释。
