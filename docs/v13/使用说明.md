# v1.3 操作说明

当前仍以规则匹配和独立人工复核为主。新入口均在左侧“发布与协作”中，已有导入、审核、补数、发布、下载流程继续可用。

## 1. 从统一待办开始

点击“统一待办”，查看待补资料、发布阻断、标准库影响及交付异常。可筛选分派给自己的记录。主管或管理员可以按原因转交给具备对应权限的成员；转交不会自动授予审核、发布或集成权限。

“打开处理”会进入原业务页面。待办显示原业务状态，不需要另行勾选“完成”。未配置电子交付的发布影响会保留“平台内处置完成”，不会宣称下游已应用。

## 2. 标准库变更与影响处置

管理员选择同一商品库的原、新已发布版本，点击“准备待确认对应”。后台生成建议，页面每次读取 20 条，可继续之前的任务。

建议分为身份及内容一致、名称或展示变化、身份字段变化、尚未对应。相同 SKU 仅用于建议，仍需人工确认；编号改变的同一商品可搜索新商品手动对应。每次确认填写依据。修改一条后先点“确认本条”，再进行分组确认。

所有分组确认后，核对完整停用范围，在数字框中明确填入停用数量，再提交影响分析。不能把未加载或未确认的记录直接当作停用。分析过程会保留输入哈希、阶段进度和失败原因；后台可重试，同一请求不会产生重复影响待办。

“处理影响”显示原商品、受影响来源和旧审核依据：

- **记录复核**：在新标准库下完成同一来源或其补数后代的有效审核，再选择该审核记录。
- **发布处置**：先生成同批次的新发布，覆盖全部受影响稳定来源并完成新库审核。文件全部就绪、发布有效后选择该版本；也可以选择原发布已有的有效撤销事件。
- 填写理由，点击“完成前检查”。范围不足、无关来源、审核未完成、发布不适用等情况会说明缺项，检查通过后才保存。

一个标准商品影响两条来源时，必须覆盖两条，不能用一条审核关闭整份发布。平台内处置与下游回执分开跟踪。旧发布 CSV 和快照不会被改写。

## 3. 回执超时与对账

集成管理员在“系统交付 → 接收系统 → 回执设置”设置业务回执期限（默认 900 秒）及负责人。可选填入符合出站白名单的回执查询地址。

HTTP 2xx 表示通知已接收；期限过后，后台扫描将其转为“回执超时，待对账”。扫描每 30 秒运行，每轮最多处理 100 条超期记录；超过一轮容量的积压需要继续扫描，监控中会保持超期告警。

点击“处理对账”，核对接收端发布编号、基线、行数和摘要，再记录“已核对”或“等待对端”。配置查询接口时可以请求自动查询。此操作不会直接把交付改为成功。只有经账号鉴权、事件绑定的业务回执才能更新实际应用结果。

对账后可重放；业务事件号保持不变，通知尝试另有编号。超时或重放后的回执必须携带 `applied_release_id`、`base_release_id`、`snapshot_hash`。旧客户端普通未超时回执仍兼容，但不能作为平台独立核验对端数据库的证据。

查询协议：平台向配置地址发送带原通知签名机制的 POST，正文包含 `event_id` 和 `delivery_id`；对端返回标准回执 JSON，包含事件、状态、实际发布、基线和快照摘要。不跟随重定向，出站地址继续受 HTTPS/DNS 白名单约束。对端无法查询时使用人工对账。

## 4. 回收供应商补充资料

数据专员从待办或商品工作台进入“补充本条资料”，下载新版问题行模板。固定列包含问题编号、来源、运行、输入版本、审核版本、草稿版本及校验值。

回填时保留固定列，填写修正字段和“资料来源”；可以调整行顺序，保存为 CSV 或单工作表 XLSX。上传回填后，系统原子校验整份文件，再生成或更新当前操作人的补数草稿。未知或被修改的编号、重复问题、旧审核/草稿版本、公式以及缺少依据会被拒绝，不留下半份草稿。

相同文件再次上传会明确提示已回收，返回原草稿，避免重复创建。模板属于下载它的组织、操作人及运行；换人接手应重新下载。最后由数据专员核对并手动提交，生成独立补数版本，仍需审核员复核。

## 5. 质量与搜索

供应商质量显示周期内输入版本总数、快照覆盖数、已加载版本数，并支持“加载更多输入版本”。完整输入和补数子集分开累计；同一来源跨版本出现不作为独立商品数。

问题明细和发布增量均已物化。翻页读取已生成的明细；质量快照会展示统计时间以及过期提示，可点“更新统计”请求后台刷新。直接子版本、最长修正链、累计补数版本分别显示。“处理历时”包含排队和等待，不代表人工净工时。

商品查询默认优先精确 SKU；接口另外支持 `mode=exact/prefix/fuzzy`，分别用于精确编码、规范化型号前缀和模糊查询。PostgreSQL 索引计划与中文查询在目标环境仍需实测。

## 6. 运行与升级

从当前 v1.2 升级前停止旧 API 和 Worker，执行 `python -m scripts.upgrade --backup <新的备份目录>`，再使用 v1.3 页面和服务启动。迁移头为 `b86fd0144e45`。脚本会校验已知表结构，未知结构会保留备份并拒绝盲目盖章。

设置 `DB_AUTO_CREATE=false` 可要求服务只使用迁移后的结构；Compose 已采用此设置。旧版已收到通知但未回执的交付获得升级后 15 分钟的对账宽限；旧接收时间使用原创建时间估算，并标记 `MIGRATED_AWAITING`。旧版仅凭单条审核关闭的发布影响会重新打开，原处置依据保留供核查。

已有发布可运行 `python -m scripts.backfill_v13` 生成增量物化和质量快照，不改旧 CSV 字节。恢复目录的交付保护文件应保持，先对账再按既有恢复流程解除。

生产依赖栈、告警到人的实际触发解除、PG/MinIO 完整恢复、真实 ERP 和真人试用尚需企业环境验收。模板见“真人试用与目标数据采集”。
