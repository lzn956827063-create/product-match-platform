# 运行维护与部署

> 当前版本为 v1.2，最新功能、实测范围和升级步骤见 [企业试用版使用说明](企业试用版使用说明.md)、[验收报告](企业试用优化验收报告.md) 和 [运行与验收](企业试用运行与验收.md)。本文保留旧版历史记录。

> 本文保留 1.0 交付的历史口径。1.1 的当前功能、接口变化和验证结果见 [优化版使用说明](优化版使用说明.md) 与 [优化交付验收报告](优化交付验收报告.md)。

本地模式已实际运行与测试。Docker Compose 提供 PostgreSQL、Redis、Celery、MinIO 的部署配置，当前交付环境没有 Docker，因此该组合的运行、故障切换和恢复尚未实测。

## 本地服务

`python -m scripts.dev --seed` 启动 127.0.0.1:18765 的 FastAPI 与独立任务轮询器。网页构建产物位于 `apps/web/dist/`，由 API 同源提供。开发 Vite 使用 5173 端口，代理到 18765。

默认状态与文件位于 `var/`。SQLite 开启 WAL、外键和 30 秒写锁等待。SQLite 用 `BEGIN IMMEDIATE` 保证写事务顺序；PostgreSQL 使用组织、运行和条目行锁。后台每组织最多一个活动运行，全实例最多两个，通过数据库调度锁领取。

初始管理员通过 `python -m scripts.bootstrap --org ... --email ... --name ...` 创建，密码从终端无回显读取。API 启动不会自动创建演示账号。

## 容器部署

在项目根执行 `python3 scripts/init_env.py` 生成 `.env`。执行 `docker compose up --build -d`，数据库健康后运行 Alembic 迁移，MinIO 初始化私有桶，API 就绪后 Nginx 开放 8080 端口。Redis 中断时 API 仍可持久登记运行，发件箱恢复后继续投递。

对外使用时配置 HTTPS 反向代理，设置 `ALLOWED_ORIGINS` 为实际域名并将 `COOKIE_SECURE=true`。刷新令牌放在 HttpOnly / SameSite Strict Cookie，修改会话接口需要 CSRF 请求头；访问令牌只保存在前端内存。数据库、Redis 和 MinIO 不映射主机业务端口。

`docker compose logs api worker dispatcher` 用于查看请求编号、阶段、资源编号和错误类型。日志不写访问令牌、商品原文或审核说明。`/api/v1/readiness` 检查数据库、存储与队列，队列断开显示降级；管理员可访问 `/api/v1/metrics`。

Compose 的 S3 文件键由服务器生成，不使用上传文件名作为路径。浏览器下载始终经过 API 重新授权，不暴露长期有效的公开对象 URL。

## 数据库版本

新安装执行 `alembic upgrade head`。初始迁移已在空 SQLite 数据库上实际执行，并通过 `alembic check` 确认模型无漂移；交付也提供生成 PostgreSQL SQL 的检查。

```bash
DATABASE_URL=postgresql+psycopg://user:password@host/database alembic upgrade head --sql
```

本地便捷启动会创建缺失表。如果已通过本地初始化创建全部表、但之后要引入 Alembic 管理，应先备份并核对当前结构与初始迁移一致，再执行 `alembic stamp head`。不可对未知数据库直接标记版本。

## 任务恢复

运行定义不可变，每 200 条为一个分块。领取时增加 `fence_token`、设置 120 秒租约，每 20 秒续租。计算期间每 20 条检查取消，提交结果前再次核对状态、租约和 token。分块结果与完成状态同一事务落库；旧进程失去租约后不能提交。

发件箱按至少一次投递设计。已投递但尚未完成的事件会重新投递，唯一键与分块状态去重。模拟暂时错误最多重试三次，采用 10 / 30 / 90 秒加抖动。持久失败将运行标记失败，不开放审核或正式导出。

取消时使分块 token 失效，关闭所有提交权限，再将运行置为取消。用户“重试”会创建新运行，保留原运行记录。程序不支持的规则/索引/特征版本会使任务失败，不会偷偷使用新算法重解释历史清单；重放旧版本需保留对应发布代码及依赖。

## 本地备份与恢复演练

```bash
python -m scripts.backup create /path/to/new-backup
python -m scripts.backup verify /path/to/new-backup
python -m scripts.backup restore /path/to/new-backup /path/to/new-restored-data
DATA_DIR=/path/to/new-restored-data python -m scripts.dev
```

备份使用 SQLite 在线备份 API，并在写锁内保存对象文件、模型及会话签名密钥，生成逐文件 SHA-256 清单。恢复仅允许写入不存在的新目录，不覆盖运行中的数据库。本次已验证数据库完整性、外键以及 6 个被引用对象的一致性。

模型路径属于对应发布目录。恢复实验模型后，还需保持模型登记的发布路径或重新登记到新环境；不要修改被历史运行引用的模型。

## PostgreSQL 与对象存储备份

以下是生产环境待演练的操作流程：

1. 暂停入口写请求和 worker / dispatcher，确保没有仍在提交的任务。
2. 在 PostgreSQL 容器内使用 `pg_dump -Fc` 保存数据库，在 MinIO 容器或有授权的维护环境使用 `mc mirror` 备份私有桶，另存 `.env`、应用数据卷和对应代码/模型发布包。
3. 记录数据库备份摘要、对象清单、模型摘要、代码版本和备份时刻。
4. 在隔离环境新建数据库及存储桶，使用 `pg_restore` 和对象清单恢复，核验外键、文件摘要、登录、任务详情和导出下载。
5. 对过期租约执行恢复验证后再开放工作进程，记录实际丢失窗口和恢复时间。

建议每日备份并周期演练。RPO 24 小时、RTO 4 小时仍是目标，当前没有完成对应生产环境的演练，不能声称已达到。

导出过期后拒绝下载；原文件、标准库、索引定义及模型有历史引用时不自动清理。备份包含认证和业务数据，应按组织自身的数据保留规则保存。
